# Greetings — Backend Specification

**Status:** Approved · **Phase:** 1 (backend only) · **Last updated:** 2026-08-08

---

## 1. Product

Greetings is a platform for older, less tech-savvy Indian users to browse, search, and download
simple status images — good-morning messages, festival wishes, devotional quotes — for sharing on
WhatsApp. Graphic designers produce the content, admins approve it, and end users consume it
exclusively through a mobile app.

### 1.1 Actors

| Actor | Platform | Capabilities |
|---|---|---|
| **User** | Mobile only | Sign in, onboard (region + languages), browse feed, search, download, share, report |
| **Designer** | Web only | Upload images, tag, submit for review, view own analytics |
| **Admin** | Web only | Approve/reject submissions, resolve reports, remove content |
| **Super Admin** | Web only | Assign roles by email/phone, view platform-wide analytics |

End users never touch the web app. Designers, admins, and super admins never touch the mobile app.

### 1.2 Delivery phases

1. **Phase 1 (this document):** backend only — Elysia + Bun + Postgres + Drizzle.
2. **Phase 2:** Next.js web panels for designers, admins, super admins. Same author.
3. **Phase 3:** React Native app for end users. **Built by a different developer**, consuming the
   OpenAPI contract this backend generates.

Phase 3's separate authorship is the main architectural constraint: the API contract must be
self-describing and stable, because it is handed across a team boundary rather than co-evolved.

## 2. Locked decisions

| Decision | Choice | Rationale |
|---|---|---|
| Media storage | Cloudflare R2 + presigned uploads | Zero egress cost for an image-heavy Indian audience; backend never proxies bytes |
| API contract | REST + generated OpenAPI | The mobile developer gets browsable docs and can codegen a client |
| Phone auth | Firebase Phone Auth | Offloads OTP delivery and DLT compliance to Google |
| Analytics region | User profile, set at onboarding | Deterministic, no geo-IP dependency, doubles as the feed personalization signal |

### 2.1 Accepted cost: Firebase ↔ Better Auth

Better Auth has no Firebase provider. Mobile sign-in therefore requires a hand-written exchange
endpoint: verify the Firebase ID token, find-or-create the user, mint a Better Auth session. This is
custom code the project owns, isolated behind a `TokenVerifier` port so it stays testable. Web
sign-in uses Better Auth's native Google provider and needs none of it.

## 4. Data model

All tables in `packages/db/src/schema/`, one file per group.

### 4.1 Auth (`schema/auth.ts` — Better Auth owns these)

- `user` — id, name, email, emailVerified, image, **role** (`user|designer|admin|super_admin`,
  default `user`), createdAt, updatedAt
- `session`, `account`, `verification` — Better Auth defaults
- `role_invites` — id, email?, phone?, role, invitedBy, createdAt, consumedAt?, consumedByUserId?

`role` is added via Better Auth's `additionalFields`. It is **never self-assignable**: only a super
admin mutates it, and the field is stripped from all client-supplied payloads.

`role_invites` exists because super admins grant roles by email or phone to people who have not
signed up yet. The grant is consumed automatically at that person's first sign-in.

### 4.2 Profile and reference data (`schema/profile.ts`)

- `user_profiles` — userId (PK/FK), phone?, displayName, regionCode → `regions`, onboardedAt
- `user_languages` — userId, languageCode (composite PK)
- `regions` — code (`IN-MH`), name — seeded with Indian states and union territories
- `languages` — code (`hi`, `mr`, `ta`), name, nativeName

### 4.3 Content (`schema/content.ts`)

- `content` — id, designerId → user, title, description?, status, primaryLanguage → languages,
  **regionCode? → regions (null = global)**, downloadCount, visibilityHold, submittedAt?,
  reviewedAt?, reviewedBy?, rejectionReason?, publishedAt?, removedAt?, createdAt, updatedAt
  - generated column `titleTsv` (tsvector, `simple` config) + GIN index
  - `pg_trgm` index on `title` for typo tolerance
- `content_assets` — id, contentId, storageKey, mimeType, width, height, bytes, checksum, createdAt
- `tags` — id, slug, label, category (`festival|language|region|theme|occasion`), isActive
- `content_tags` — contentId, tagId (composite PK)

### 4.4 Moderation (`schema/moderation.ts`)

- `reports` — id, contentId, reporterId, reason
  (`inappropriate|copyright|spam|wrong_info|other`), note?, status
  (`open|resolved_kept|resolved_removed`), createdAt, resolvedAt?, resolvedBy?, resolutionNote?
  - partial unique index on (contentId, reporterId) `WHERE status = 'open'` — one open report per
    user per item
- `moderation_actions` — id, actorId, contentId, action (`approve|reject|remove|restore`), reason?, createdAt
- `role_change_log` — id, actorId, targetUserId, fromRole, toRole, createdAt

### 4.5 Analytics (`schema/analytics.ts`)

- `download_events` — id (bigserial), contentId, **designerId**, userId, **regionCode**,
  languageCode?, source (`feed|search|detail`), createdAt
  - indexes on (designerId, createdAt), (contentId, createdAt), (regionCode, createdAt)
- `daily_content_stats` — statDate, contentId, designerId, regionCode, downloads, uniqueUsers
  - PK (statDate, contentId, regionCode)

`designerId` and `regionCode` are denormalized onto `download_events` deliberately. It makes every
analytics query a single-table scan, and it freezes region attribution at event time — if a user
later moves states, history stays correct.

## 5. Content lifecycle

```
draft ──submit──▶ pending_review ──approve──▶ published ──remove──▶ removed
                        │                         ▲                     │
                        └──reject──▶ rejected ────┘ (resubmit)          └──restore──▶ published
```

All transitions go through a single `transition()` function in the content module — never inline in
route handlers. Every transition writes a `moderation_actions` row. Illegal transitions return
`409 CONFLICT`; they never silently no-op.

Submission requires a title, at least one confirmed asset, and at least one tag.

## 6. Upload flow

The backend never handles image bytes.

1. `POST /v1/designer/content` → creates draft, returns `contentId`
2. `POST /v1/designer/content/:id/upload-url` `{ mimeType, bytes }` → validates mime
   (`jpeg|png|webp`) and a 10 MB cap, returns an R2 presigned PUT URL and `storageKey`
3. Client `PUT`s directly to R2
4. `POST /v1/designer/content/:id/assets/confirm` `{ storageKey, width, height }` → backend `HEAD`s
   the object to confirm it exists with the expected size and content type, then records the asset
5. `POST /v1/designer/content/:id/submit` → `pending_review`

Thumbnails come from Cloudflare Image Resizing URL parameters at the CDN edge — no backend image
processing and no variant pipeline.

A cleanup job removes drafts with no confirmed asset after 7 days and purges their R2 objects.

## 7. Feed and search

`GET /v1/feed?cursor=&limit=` returns published, non-held content scored in SQL:

```
score = 2.0 × (content.primary_language ∈ user.preferred_languages)
      + 1.5 × (content.region_code = user.region_code)
      + 1.0 × (content.region_code IS NULL)        -- global content is always eligible
      + recency_decay(published_at, half_life = 7d)
      + 0.5 × ln(1 + downloads_last_7d)
```

The global-content term is what guarantees a user in an underserved region never sees an empty feed.

### 7.1 How it is executed

The score above is the definition. Computing it that way — per row, per request, with a lateral
count over `download_events` for every published item — was measured at **4,684 ms a page** against
200,000 published items and 2,000,000 events. That is unusable, and at a tenth the catalogue it is
still half a second.

The score splits in two:

```
base   = recency_decay(published_at) + 0.5 × ln(1 + recent_downloads)   -- same for every viewer
bonus  = 2.0 × language match + 1.5 × own region + 1.0 × global         -- one of six constants
```

`base` is stored on `content.base_score`. Because `bonus` takes only six values, the catalogue
divides into six groups, and *within a group the ranking order is exactly `base_score` order* —
which an index already holds. So the feed is six (or a few more, see below) index seeks that each
read one page and stop, merged and re-ranked. Any item in the true top N is in its own group's top
N, so this is an optimisation, not an approximation: the result is identical to scoring everything.

Measured on the same 200k/2M dataset:

| | before | after |
|---|---|---|
| feed page, viewer with region and 2 languages | 4,684 ms | **3.4 ms** |
| second page by cursor | — | 3.6 ms |
| viewer who has not onboarded | — | 2.6 ms |
| viewer with 6 languages | — | 61 ms |
| nightly rescore of all 200k items | — | 18 s |

Three details are load-bearing and easy to lose:

- **One branch per language, not `= ANY`.** A parameterised array cannot be combined with the
  ordering, so Postgres reads the whole group and sorts it. Equality on a single value lets it walk
  the index in order and stop. This is why cost grows with the viewer's language count.
- **`ORDER BY … DESC NULLS LAST`.** Plain `DESC` means `NULLS FIRST` in Postgres, which does not
  match how the indexes are built, and the planner silently falls back to a sort. Both columns are
  `NOT NULL`, so this changes nothing about the result — only about whether the index is usable.
- **The three partial indexes** on `content`, all `WHERE status = 'published' AND visibility_hold =
  false`: `(base_score)`, `(primary_language, base_score)`, `(region_code, base_score)`.

**What this costs.** `base_score` is a stored value, so it can be stale.

- Popularity is *not* stale: a download bumps the counter and the score in the same statement that
  was already running. What the nightly pass does is the part an increment cannot — retire downloads
  that have aged out of the seven-day window.
- Recency decays continuously but is only rewritten nightly. Between refreshes every item's recency
  term shrinks by the same factor (≈0.91 over a day), so the ordering *by recency* is untouched;
  only its weight against popularity drifts, by under a tenth of a point.
- Newly published content is scored inside the transaction that publishes it, so nothing waits a day
  to appear.
- **Anything that writes `published_at` outside the publish path must re-run the refresh.** Nothing
  in the application does; the demo seed and some tests do, and they call it.

**Pagination stability.** The cursor is `(score, id)` and nothing more. It used to carry an
hour-quantised clock, because scores were computed from `now()` and two pages of one session ranked
against slightly different clocks — items could slide across the boundary and be skipped. Stored
scores do not move between requests, so there is no clock left to pin.

The per-group keyset uses `<=` rather than `<` on `base_score`, deliberately: subtracting a bonus and
adding it back is not exact in floating point, and a strict comparison there could drop the row the
next page should start with. The outer query applies the exact strict test against the score as it
was issued, so no row can repeat.

### 7.2 Search

`GET /v1/search?q=&tags=&language=&region=&cursor=` — full-text match on `titleTsv`, trigram
fallback for misspellings, tag filtering via join, ordered by `ts_rank` then recency.

Search is *not* on the same footing as the feed: it still evaluates its predicate over the matching
set rather than reading a prepared order. Measured at 200k items it is ~98 ms for a term and ~157 ms
for a misspelling, which is acceptable for a query a user types and waits for, and is the next thing
to look at if the catalogue grows another order of magnitude.

## 8. Downloads

`POST /v1/content/:id/download` is the **only** route to image bytes:

1. Verify content is published and not held
2. Insert a `download_events` row, stamping designerId and the user's profile region
3. Atomically increment `content.downloadCount`
4. Return a signed R2 URL valid for 5 minutes

Because objects are not publicly hotlinkable, every download passes through this endpoint — which is
what makes the counts trustworthy rather than an undercount. Clients send an `Idempotency-Key`
header; a repeat within 60 seconds returns the same URL without double-counting a retry.

## 9. Analytics

| Endpoint | Audience |
|---|---|
| `GET /v1/designer/analytics/summary` | Designer — own totals over a date range |
| `GET /v1/designer/analytics/by-content` | Designer — per-post |
| `GET /v1/designer/analytics/by-region` | Designer — regional breakdown |
| `GET /v1/designer/analytics/timeseries` | Designer — daily/weekly trend |
| `GET /v1/admin/analytics/overview` | Super admin — users, designers, images, downloads |
| `GET /v1/admin/analytics/by-designer` | Super admin — per-designer performance |
| `GET /v1/admin/analytics/{by-content,by-region,timeseries}` | Super admin — platform-wide |

Designer endpoints force `designerId = session.userId` server-side. The client cannot supply it, so
a designer cannot read another designer's numbers.

Queries read `daily_content_stats` for dates before today and `UNION ALL` a live aggregation over
`download_events` for today. The nightly job recomputes yesterday idempotently
(`INSERT … ON CONFLICT DO UPDATE`), so re-runs and backfills are always safe.

## 10. Reporting and moderation

- `POST /v1/content/:id/report` — rate-limited, one open report per user per item
- At **5** open reports on one item, `visibilityHold` is set automatically and the item drops out of
  the feed pending review. This is the safety valve that stops bad content spreading between admin
  sessions.
- `GET /v1/admin/reports?status=open` — grouped by content, worst first
- `POST /v1/admin/reports/:id/resolve` `{ action: keep|remove, note }`

## 11. Authentication

### 11.1 Mobile (end users)

1. The RN app completes Firebase Phone (or Firebase Google) sign-in and receives an ID token
2. `POST /v1/auth/firebase` `{ idToken }`
3. Backend verifies the token against Google's public JWKS using `jose`, asserting `iss`,
   `aud === FIREBASE_PROJECT_ID`, and expiry. `jose` rather than `firebase-admin`: signature
   verification is all we need, and it keeps the Bun runtime lean.
4. Find-or-create the user via an `account` row (`providerId: 'firebase'`, `accountId: <firebase
   uid>`), linking by phone/email on match, and consume any matching `role_invites`
5. Mint and return a Better Auth session

### 11.2 Web (designers, admins, super admins)

Better Auth's native Google social provider. **Email/password is disabled** — the scaffold enables it
by default and it must be turned off. Web routes reject `role === 'user'`.

### 11.3 Enforcement

A `requireRole(['designer'])` Elysia macro resolves session → user → role and returns 401 or 403.
Every non-public endpoint carries one explicitly; there is no default-allow path.

Token verification sits behind a `TokenVerifier` port, so tests never call Google.

## 12. Cross-cutting

- **Versioning** — every route under `/v1` from day one
- **API docs** — Elysia's OpenAPI plugin generates the spec from `t.Object` schemas, served at
  `/docs`. This generated document *is* the contract handed to the mobile developer.
- **Errors** — one envelope, `{ error: { code, message, details? } }`, closed set of codes
- **Pagination** — opaque base64 cursors everywhere; no offset pagination
- **Env** — `packages/env` validates with `@t3-oss/env-core` + zod and fails fast at boot
- **Logging** — structured, via the `evlog` addon wired into `apps/server/src/index.ts`
- **Ports for external dependencies** — `ObjectStorage` (R2) and `TokenVerifier` (Firebase) are
  interfaces with in-memory test doubles, so the suite runs hermetically

### 12.1 Rate limiting

Two layers, because neither works alone.

**Per address** is the obvious one and the weaker. Behind a proxy the socket address is the proxy's,
so the real client is in `x-forwarded-for` — but a client talking to this server *directly* sets
that header itself, and a limiter that believes it can be evaded by changing it each request. So the
forwarded headers are read only when `TRUST_PROXY_HEADERS=true`, which a deployment sets when
something in front of it overwrites them. It defaults off: the unsafe direction should take a
deliberate act.

Even trusted, the per-address limit has to be loose here. Indian mobile carriers use carrier-grade
NAT, so one address fronts thousands of genuine users — sign-in allows 600/minute per address for
that reason, not by accident.

**Global** is the one that holds under attack: a ceiling on how much of an expensive operation the
process will do per minute in total, regardless of who asks. Sign-in verification is capped at
6,000/minute — a hundred a second, far past anything this product will see — so evading the address
limit buys nothing, and past the ceiling callers are refused in microseconds instead of the server
queueing signature checks until it falls over.

Authenticated endpoints key on user id, which no header can forge. Downloads allow 120/minute per
user; reporting is limited durably in the database (20/hour) because that limit protects the admin
queue rather than the server and must survive a restart.

The store is in-process, which is a deliberate limitation: counters are per instance, so N instances
allow N times the limit, and they reset on restart. Neither matters for a single container. When it
stops being one, replace the store behind the `RateLimitStore` interface — no call site changes.

### 12.2 Behaviour under load

The intent is that the server gets slower and then refuses work, rather than falling over.

- **Connection pool, default 10.** More is not faster: past roughly twice the core count, Postgres
  backends contend for the same CPUs and every query slows without any finishing sooner. Requests
  queue at the pool, which is where queueing belongs — ten queries running and the rest waiting
  finishes more work than two hundred running at once. `DATABASE_POOL_MAX` exists because the right
  number is a property of the machine.
- **Bounded wait for a connection** (5 s). An unbounded queue holds sockets open for work whose
  caller left minutes ago.
- **`statement_timeout`** (15 s default). A query with no ceiling holds its connection until it
  finishes, and a disconnected client does not stop it. Batch jobs raise this for their own
  transaction only, via `set_config(..., true)`, so the request-path ceiling is never widened.
- **`idle_in_transaction_session_timeout`.** A transaction left open by a crashed process holds its
  locks and pins the vacuum horizon indefinitely.
- **Request body limit** (1 MB default). Bun buffers a body in memory before any handler or schema
  sees it, so without a ceiling a few large POSTs are an out-of-memory kill rather than a 413.
  Nothing legitimate comes close: images go straight to R2 and never pass through this process.
- **Graceful shutdown.** SIGTERM stops the listener and waits for in-flight requests, with a 10 s
  backstop. Without it a deploy kills requests mid-flight — a download counted but never returned.
- **UTC pinned on every connection.** Every timestamp column is `timestamp without time zone` and
  the analytics rollup buckets by UTC calendar day, so the day boundary has to belong to the
  application rather than to whatever the host clock is set to.
- **Idle-client errors are handled.** An error on an idle pooled connection — the database
  restarting, a network blip — is an unhandled `error` event, and node's default for that is to
  crash the process. The pool recovers on its own; the process would not.

Measured query counts per request: `GET /v1/feed` is 4 (session, user, preferences, feed);
`GET /v1/auth/me` is 2. Web panel requests inside the cookie-cache window are 0 for auth, because
the signed cookie carries the session and role.

### 12.3 Scale ceilings, honestly

- The feed is bounded by index reads and is not sensitive to catalogue size; it *is* sensitive to
  how many languages a viewer selects (one branch each).
- Search still scans its matching set. ~98 ms at 200k items; revisit past a million.
- `download_events` is the fastest-growing table and is never pruned. Analytics read the daily
  rollup for past dates, so query cost does not grow with it, but disk does. Partitioning by month
  is the obvious next step and is not done.
- `platformOverview` runs four unqualified `COUNT(*)`s. Fine for an admin dashboard at this size;
  it will need caching before it needs rewriting.
- The rate limiter and the session-resolution cache are per process. Running more than one instance
  changes both, as described above.

## 12.4 Audit trail

Every privileged action leaves a record, written by the code that performs it rather than by a
separate logging layer that could be forgotten:

| What | Where | Written by |
|---|---|---|
| Who created a piece of content | `content.designer_id`, `created_at` | the create route |
| Every lifecycle move, with reason | `moderation_actions` | `transition()`, in the same transaction |
| Who reviewed, and when | `content.reviewed_by`, `reviewed_at`, `rejection_reason` | `transition()` |
| Who reported, and why | `reports` | the report route |
| Who ruled on a report | `reports.resolved_by`, `resolved_at`, `resolution_note` | the resolve route |
| Every role change, from and to | `role_change_log` | `applyRoleChange`, and invite consumption |
| Invites offered and withdrawn | `role_invites`, incl. `revoked_at`/`revoked_by` | the roles routes |
| Who downloaded what, when, from where | `download_events` | the download route |

Two rules the design depends on:

- **Append-only.** A correction is a new row, never an edit. `moderation_actions` has no update path.
- **Ids, not names.** The log stores actor ids; names and emails are resolved when it is read. An
  audit that recorded a display name would quietly rewrite itself when that name changed.

Revoking a role invite is a soft revoke for the same reason — a `DELETE` that leaves no trace is a
hole in the trail, and "a super admin offered someone admin and thought better of it" is exactly
what the trail is for. The unique index ignores revoked rows so the address can be invited again
immediately, and the sign-in path skips them so a withdrawn invite cannot still grant.

**Reading it.** The records existed from M2 onwards but were reachable only through psql, which is
not an audit trail so much as the raw material for one. The endpoints:

| Endpoint | Who | What |
|---|---|---|
| `GET /v1/admin/content/:id/audit` | admin | one item's whole story: creation, every lifecycle move, every report and resolution, merged into one timeline newest-first, each with the person behind it |
| `GET /v1/admin/audit/roles` | super admin | every role change ever made |
| `GET /v1/admin/audit/actions` | admin | recent decisions across all content, filterable by moderator or action |
| `GET /v1/admin/content` | admin | search every status — the way *in* to a specific item |
| `GET /v1/admin/users` | admin | find a person, see their role and when it last changed |

The timeline is one query with four `UNION ALL` branches rather than four round trips stitched
together, so its ordering is the database's and cannot disagree with itself. `actor` is null where
the system acted alone — currently only the automatic hold, and attributing that to an admin would
be a lie.

**Known limits.** Deleting content cascades its audit rows away; only drafts are ever deleted, by
the designer or the orphan sweep, and nothing deletes published content. Per-user download history
is recorded but deliberately not exposed — analytics answer the questions the product asks, and a
"what has this person downloaded" screen is a surveillance feature nobody requested. Session
IP/user-agent are captured by Better Auth but not surfaced.

## 13. Testing

`bun:test`, integration-first: real Postgres from Docker Compose, migrations applied per run, tables
truncated between tests. Mocking the database would leave the genuinely risky logic untested — the
ranking SQL, rollup arithmetic, and partial unique constraints are exactly where bugs will live.

Non-negotiable coverage:

- **Every role guard** — each endpoint against each wrong role
- **Every lifecycle transition**, including illegal ones
- **Feed pagination stability**: no duplicates, no gaps, and identical ordering across requests
- **Download idempotency** under a repeated `Idempotency-Key`
- **Rollup correctness** — `daily_content_stats` must equal a live aggregation of the same raw events
- **Adversarial probes** (`test/adversarial.test.ts`) — tampered cursors, rate-limit evasion,
  concurrent approval and concurrent report resolution, account-linking collisions, oversized bodies.
  Every test in that file was written to fail first; the ones that passed stayed because the
  property is worth pinning down.
- **The audit trail** (`test/audit.test.ts`) — that after an item has been through the mill, a super
  admin can say who did each thing and why, without opening a database client

## 14g. Constraints discovered during the hardening pass

Each of these began as a test written to fail, or a measurement that contradicted an assumption.

**A parameterised `= ANY` cannot be combined with an ordering.** Postgres reads every row in the
group and sorts. Splitting into one equality branch per value was the difference between 18 ms and
0.2 ms per branch.

**`ORDER BY x DESC` is `DESC NULLS FIRST`; Drizzle's `.desc()` emits `DESC NULLS LAST`.** They do
not match, so the planner silently ignores the index and sorts. Nothing about this appears in the
plan as an error — it just costs a hundred times more. Any query meant to ride an index built with
`.desc()` must spell out `NULLS LAST`.

**`SET LOCAL` takes no bind parameters.** Use `SELECT set_config(name, value, true)`, whose third
argument is what makes it transaction-local.

**Forwarded headers are client-controlled unless a proxy overwrites them.** Rate limiting that
trusts them unconditionally is decoration. See §12.1.

**Cursors are bound into `::timestamp` casts.** A string Postgres cannot parse leaves as a 500, so a
tampered cursor pages whoever is on call for what is really a malformed request. Cursor timestamps
are parsed in TypeScript before they reach the database.

**The bucket, not the database, knows what was uploaded.** Cleanup driven by `content_assets` walks
straight past objects that were presigned and PUT but never confirmed — a designer who uploads and
closes the tab. Sweeping by key prefix is the only version that terminates.

**A `DELETE` on an invite erased the audit trail.** Soft revoke instead, with the partial unique
index and the sign-in path both taught to ignore revoked rows. The second of those is easy to
forget and would have left withdrawn invites still granting.

**CORS listed the methods the panels use, minus `PUT`** — which two live routes use. A browser
preflight refuses before the request is ever made, so nothing server-side would ever have logged it.

**A rejection with no edit endpoint is a dead end.** The reviewer tells the designer exactly what to
fix and the designer has no way to fix it. Editing is confined to `draft` and `rejected`: an
approval is of specific words, and letting them change afterwards would make review theatre.

**Postgres cancelling a statement is the timeout working.** The nightly rescore hit the request-path
`statement_timeout` at 200k rows. Batch work opts out for its own transaction rather than the
ceiling being raised for everyone.

## 14a. Constraints discovered while building M1

Non-obvious behaviours that shaped the code. Each is enforced by a test or a comment at the
relevant line, but they are recorded here because they will otherwise be rediscovered the hard way.

**`evlog/elysia` must not be imported by anything under test.** It creates an `AsyncLocalStorage`
via `enterWith()` at module scope, which permanently rebinds the async context and stops Bun's test
runner from ever marking the *next* test complete — the symptom is an unrelated, often synchronous,
test timing out. `createApp()` in `apps/server/src/app.ts` is therefore free of logging, and
`index.ts` layers evlog on top. Keep it that way: any future module that imports `evlog/elysia`
becomes untestable, and takes its importers with it.

**Unmatched routes need a real catch-all route, not `onError`.** The evlog plugin drops the body of
the response produced by the `NOT_FOUND` branch of `onError`, turning production 404s into an empty
body with no envelope. `createApp()` ends with an `.all("/*")` route instead. Tests alone would not
have caught this — it only appears once evlog is mounted, which the tests deliberately avoid, so it
was found by curling a running server. Verify error paths against a real server, not just
`app.handle()`.

**`tsc -b` must not emit JavaScript.** With `composite: true` and `outDir: dist`, `check-types`
compiled the test files into `dist/`, where `bun test` collected and ran them a second time — the
suite silently reported double the tests. `emitDeclarationOnly: true` in
`apps/server/tsconfig.json` prevents it; `tsdown` still produces the real build.

**Postgres 18 images changed their volume convention.** The data volume mounts at
`/var/lib/postgresql`, not `/var/lib/postgresql/data`; the old path makes the container
restart-loop.

## 14b. Constraints discovered while building M2

**An unverified email is not an identity.** Sign-in links accounts by email only when the provider
reports it verified — otherwise anyone able to type an address could claim the matching account.
The same rule governs *writing* `user.email`: that column is unique, so storing an address is itself
an identity claim. An unverified address is therefore replaced by a
`<firebase-subject>@firebase.placeholder` value, which also avoids a unique-constraint 500 when the
real owner already has an account. A test asserts both halves; do not relax either.

**Roles come from the session, not a separate query.** `auth.api.getSession()` already returns the
user with `role` on it, so the extra lookup that used to follow it was pure waste. Authorisation now
reads `session.user.role`.

Two facts govern how this behaves, and they are easy to get wrong:

- **Better Auth's session token is not a JWT.** It is a signed *opaque* token used as a database
  lookup key. There is no claim to read statelessly by default. Each `getSession()` is two
  queries — the session row, then the user row.
- **`session.cookieCache` is the stateless path**, and it is enabled with `strategy: "jwt"` and a
  five-minute TTL. It applies to cookie-bearing web requests only; mobile clients send a bearer
  token and no cookie jar, so they still resolve through the database — where the user row is
  re-read, meaning their role is always current.

Because a cached cookie can carry a stale role for up to its TTL, **every role change deletes the
target's sessions**. A demotion therefore takes effect on the next request rather than whenever the
session would have expired. Changing a role by writing to the database directly skips that, so
privilege changes must go through the role-assignment endpoint.

**Resolve the session once per request.** Both the authorisation guard (mounted by every route
module) and the request logger need it. Left alone they each pay for their own lookup: measured
against a real server, one authenticated request issued six queries, then four. `getSessionOnce`
memoises on the Request object and brings it to two — and to zero for a web request served from the
cookie cache. Note evlog's `createAuthMiddleware` resolves its own session; pass an
already-resolved one to `identifyUser` instead.

**Drizzle wraps driver errors.** A Postgres unique violation does not arrive with `code` on the
thrown object — SQLSTATE `23505` sits somewhere down the `cause` chain. Code that maps constraint
violations to `409 CONFLICT` must walk that chain, or the violation surfaces as a 500.

**`role` carries `input: false` in the Better Auth config.** Without it, a sign-up payload could
name its own role. This is the security boundary of the entire role system.

## 14c. Constraints discovered while building M3

**`t.Optional(t.UnionEnum([...]))` is not optional.** When the parameter is absent it resolves to
the *first* value in the list rather than `undefined`. A `status` or `category` filter written that
way silently filters every listing to one value, which reads as a short result rather than an error
— `GET /v1/tags` returned only festivals, and `GET /v1/designer/content` only drafts. Use
`optionalEnum()` from `apps/server/src/lib/schema.ts`, which wraps `t.String({ enum })` and keeps
the narrow static type via `t.Unsafe`. Required enum fields are unaffected.

The lesson generalises: a test that asserts *"everything returned matches the filter"* passes
happily when the filter is stuck on. Assert the set of values actually present instead.

**Trust the object, not the client.** The upload flow takes a declared size and MIME type when
issuing a presigned URL, but records what R2 reports once the object lands — the two can differ, and
only the storage layer knows the truth. Confirmation also checks the key is prefixed
`content/<id>/`, without which a designer could attach another designer's object to their own post.

**Delete objects before rows.** The orphan-draft job removes R2 objects first and only then the
rows. The storage key exists solely on the row, so deleting the row first would leak the object
permanently. When a delete fails, the row is deliberately kept so the next run retries.

**Bun ships an S3 client**, and R2 speaks S3, so storage needs no dependency — `new S3Client({
endpoint: "https://<account>.r2.cloudflarestorage.com", region: "auto" })`. Presigning is pure
computation, so `test/storage.test.ts` exercises the real adapter with throwaway credentials while
every other test uses the in-memory fake.

## 14d. Constraints discovered while building M4

**`similarity(title, q) > 0.25` cannot use a trigram index; `title % q` can.** Written the first
way, the fuzzy fallback seq-scans every published row — confirmed with EXPLAIN, and 8× slower than
the index path on 20k rows (98ms against 12ms). The operator uses `pg_trgm`'s default threshold of
0.3; `similarity()` is still fine for *ranking* the rows the operator admits, because by then the
set is small.

**Drizzle's `sql` template flattens interpolated arrays.** `ANY(${codes})` reaches Postgres as a
scalar and fails with *malformed array literal*. Use `sql.param(codes)` to bind one parameter, and
cast it — `ANY(${sql.param(codes)}::text[])`.

**Bind numeric constants with `sql.raw`, not as parameters.** A bound `1.5` sitting beside a `CASE
… THEN 1 ELSE 0 END` makes Postgres infer `integer` and reject it outright. The scoring weights are
compile-time constants, so `sql.raw(String(value))` is both correct and more readable in logs.

**Order search by rank *then recency*.** With no search term every rank is 0, so a sort of
`rank DESC, id DESC` returns an arbitrary slice rather than the newest content — and browsing with
filters but no query is a first-class case for this audience.

**Backticks inside a SQL comment terminate the template literal.** Obvious in hindsight, invisible
in the error message.

Measured plans at 20k rows: the feed page uses `content_feed_idx` (index scan, 0.24ms). Full-text
and trigram predicates fall back to sequential scans only when a query matches a large fraction of
the table, which is the planner making the right call rather than a missing index.

## 14e. Constraints discovered while building M5

**Idempotency is claimed in one statement, not read-then-write.** The realistic failure is a flaky
mobile connection firing the same request several times before any response arrives, so a check
followed by an insert would let two of them through. The claim is a single upsert whose `setWhere`
only refreshes a row that has aged past the replay window; *no rows returned* is then an exact
answer to "someone already claimed this". A test fires eight concurrent identical requests and
asserts exactly one download is recorded.

**Download is a POST, not a GET.** It has a side effect, and browsers, proxies and link previewers
prefetch GETs freely — which would inflate the very numbers designers are measured on.

**The counter is incremented in SQL** (`download_count = download_count + 1`), never read-modify-
write. A test runs ten concurrent downloads and asserts the counter equals the event count; the
naive version loses increments.

**`languageCode` on a download event is the content's language, not the user's.** A user may prefer
several, and the question analytics needs to answer is which content travels — not what the reader
speaks. `regionCode` is the opposite: it comes from the user's profile, frozen at event time.

**Idempotency records are purged on a schedule.** One row per download would otherwise make this the
second fastest-growing table in the system. They are kept an hour — far longer than the 60-second
replay window — so they double as a short trail when diagnosing a client's retry behaviour.

## 14f. Constraints discovered while building M8

**Do not rate-limit by IP tightly in this market.** Indian mobile carriers use carrier-grade NAT, so
one address can front thousands of genuine users; a tight per-IP limit locks out a network rather
than an abuser. Sign-in allows 600/minute per address — a backstop against a client burning CPU on
token verification, not a credential guard, since Google has already authenticated the token.
Downloads are limited per *user* (120/minute) for the same reason. The test suite found this the
hard way: every test request shared one address, and a 20/minute limit failed 276 tests.

**Response schemas are declared with Elysia's `response`, not free-text documentation.** They are
validated at runtime, so the published contract cannot drift from what the server returns — a shape
change fails a test instead of surprising the mobile developer. Only the endpoints the React Native
app consumes are covered; the web panels are written in this repository against the same TypeScript
types, where a hand-maintained schema would add drift risk without adding safety.

**Test files share one database and one in-process rate-limit store.** A test that deliberately
exhausts a quota must use an address range no other file generates *and* clear the store afterwards,
or it fails unrelated files. The suite was verified stable across three consecutive full runs after
this was fixed.

**A nightly job must not abort when an optional dependency is missing.** Cleanup crashed on an
unconfigured R2 and left the rollup half-done; it now purges what it can and reports the skip.

## 15.1 What is deliberately not built

Knowing the shape of the hole matters as much as knowing what fills it.

**No refresh tokens or token rotation.** Better Auth sessions are long-lived database rows; mobile
holds one as a bearer token. Revocation is by deleting the row, which role changes already do.

**No email or push notification of any kind.** A designer learns their content was rejected by
opening the panel. There is no transport configured and no queue to put one behind.

**No image processing.** No resizing, no thumbnails, no format conversion, no moderation scanning of
pixels. Thumbnails are intended to come from Cloudflare Image Resizing URL parameters at the edge.
The backend never sees image bytes at all, which is the property that keeps it cheap — and it means
"is this image actually what the title claims" is answered by a human reviewer, not by software.

**No soft delete for content.** Removal sets a status; only drafts are ever really deleted.

**No multi-tenancy, no organisations, no teams.** Designers are individuals.

**No i18n of API responses.** Error messages are English. The *content* is multilingual; the
operator-facing strings are not, and the mobile app is expected to map error `code`s to its own
translated copy rather than display `message` — which is why `code` is a closed set.

**No caching layer.** No Redis, no CDN in front of the API. The feed is fast enough without one and
adding a cache before it is needed would mean debugging staleness for no gain.

**No per-user download history endpoint.** Recorded, deliberately not exposed. See §12.4.

**No search relevance tuning against real data.** The trigram threshold is pg_trgm's default and the
`simple` text-search configuration does no stemming, which is right for Hindi and Marathi and merely
adequate for English. This wants revisiting once there is real content to tune against.

**No admin edit of content.** An admin approves, rejects, removes or restores. They cannot fix a
designer's typo, and giving them that power would mean an approval no longer refers to a fixed
artefact.

**Response schemas are declared for the mobile endpoints only.** Those cross a team boundary — a
different developer builds against them — so they are validated at runtime and cannot drift from
the published contract. The designer, admin and super-admin routes are consumed by the web panels in
this same repository, where a type error catches the same class of mistake sooner and cheaper.

### End-to-end acceptance (after M7)

Driven entirely through the HTTP API: seed a super admin → grant a designer role by email →
designer uploads and submits → admin approves → mobile user signs in with a stubbed Firebase token
and onboards → the image appears in that user's feed → user downloads it → designer analytics shows
one download attributed to the user's region → user reports it → admin removes it → the image
disappears from the feed.
